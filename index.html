01 /

What makes this simpler?

Imagine a warehouse with shared shelves. The main app is one item, processor code another, and language resources another. Different phones need different shopping lists, but the warehouse does not make a fresh copy of every item for each list.

For the customer

They see one app and tap Install. APK Station selects the compatible files. Customers do not choose “arm64” or work out which screen-density file belongs with a base APK.

For the store team

You manage original files and the records describing them. Identical files share storage. Regional observations, device compatibility and availability are small database records instead of repeated full downloads kept forever.

  1. Collect. apkeep fetches what a particular Google Play account and submitted device profile can receive.
  2. Verify and remember. Preserve the complete returned file list, its context and actual version. Store each verified file under its SHA-256 hash.
  3. Select. The server chooses one complete, validated set compatible with the customer’s device and current catalog policy.
  4. Deliver. The Android client can fetch those files directly. For a single-file export, create or reuse an XAPK containing that selected set.

The first version should reuse complete verified captures. Sharing identical bytes does not require mixing splits from unrelated downloads. Combining pieces from different captures is a later capability that needs proof they belong to the same compatible variant.

The complexity moves into a small number of well-defined components: collector, verifier, resolver and installer. Android’s differences still exist; every customer and every screen in your product no longer needs to understand them.

What does split_apk=true actually do?

It asks apkeep to retrieve the app’s existing split delivery when available. Its documentation describes a fallback to a full APK. It does not cut a downloaded app into pieces, collect every possible variant, or create the XAPK export for you. [5]

Illustrative download for one phone:
base.apk                 → main app
config.arm64_v8a.apk      → processor-specific code
config.xxhdpi.apk         → screen-density resources
config.en.apk             → English resources

These four files are one installation set, not four separate apps.

For APK Station, package the complete verified selection. Preserve APK bytes and signatures. The outer XAPK can be built later; modifying or re-signing the inner APKs changes their trust and update identity. [19][20]

INTERACTIVE · HYPOTHETICAL INVENTORY

What exactly are the 88 files?

The default assumes two underlying binary families. Each has 1 base + 4 processor alternatives + 6 density alternatives + 30 language files + 3 optional features. That is 44 files per family × 2 = 88.

576,000Possible request contextsChoices × countries
11,520Possible different file setsUnder the model’s assumptions
88Individual APK filesUnique bytes assumed per inventory item

2 × 1 × (1 + 4 + 6 + 30 + 3) = 88 files.

One phone takes four files, or seven with all three optional features. It does not download all 88.

50 country contexts add zero files when they use the same content.

The formulas and their limits
Requests = S × A × D × L × 2^F × R
Sets = S × A × D × L × 2^F × B
Files = S × B × (1 + A + D + L + F)

These formulas assume independent choices, a file for every listed resource, a distinct inventory for every family/content group, and no further splitting inside features. Real apps can have fewer files, shared bytes across groups, multiple languages, dependency restrictions, unsplit resources or many additional assets. Country context count is not a measured APK multiplier.

The 88 is an explanation, not a measurement or collection target. Real inventory = distinct verified file hashes observed for a release. Completeness remains unknown without full publisher inventory.

04 /

How the regional phones work

Treat each phone or worker as a collector with a recorded context. Each asks Play for the app; the central store records the result and reuses identical files.

Device description

The profile tells the downloader which device it represents: Android SDK, supported ABIs, display density and relevant features. Current upstream apkeep uses an explicit profile and defaults to px_9a; it does not automatically infer these facts from the host phone. [6][7]

Regional context

Keep the Play account’s country and access, outgoing network location, and requested language separate. A French locale is not a French Play account. Account country influences availability; locale/timezone changes alone do not establish access. [12][5]

Execution and routing matter. apkeep can run on Android through Termux or on desktop/server platforms. [8] If it runs on the phone, its traffic uses that connection. If it runs on a server, configure that worker’s outbound connection and profile explicitly. Plugging a phone into the backend does not automatically apply its region or hardware settings.

Pin the downloader build and profile revision. Use a fresh output directory for every job: current upstream skips existing output and rejects explicit Google Play version requests. Parse returned manifests and record per-app success; command completion alone is insufficient. [6]

The proposed collector profile stores references to account secrets and egress configuration, not raw credentials. Stable regional contexts are easier to reason about than repeatedly changing account country. A physical phone is valuable for real installation and runtime testing; there is no requirement to own one phone for every possible file combination.

How the database will look

The database stores the lists and evidence. Object storage holds the APK bytes. Country is a property of an observation or policy; it is not part of a file’s storage key.

Example: com.example.notes has release 230 under a verified signing identity. Sets A, B and C describe English/480 dpi, French/480 dpi and English/320 dpi. All three refer to the same base and arm64 blobs. Four captures record the US, France, India and Kenya observations; the US and Kenya captures both reference A.

Two kinds of identity

File identity = SHA-256(original file bytes)
Object key    = blobs/sha256/<first-two-hex>/<full-sha256>

Set identity  = SHA-256(canonical versioned descriptor of:
  package, versionCode, signing identity,
  sorted file entries: logical role + destination + hash + required flag)

Export key    = set identity + format + packager revision + options digest

Canonical means the same input is serialized the same way, with a fixed schema and ordering. The set digest identifies content; mutable availability and compatibility evidence remain separate. Include every option that changes archive bytes in the export identity. Do not put expiring URLs or customer-specific data inside a shared archive.

CREATE TABLE apps (
  id uuid PRIMARY KEY,
  package_name text NOT NULL UNIQUE,
  display_name text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE signing_identities (
  id uuid PRIMARY KEY,
  identity_digest text NOT NULL UNIQUE CHECK (identity_digest ~ '^[0-9a-f]{64}$'),
  certificates jsonb NOT NULL,
  verified_lineage jsonb,
  trust_evidence jsonb NOT NULL
);

CREATE TABLE releases (
  id uuid PRIMARY KEY,
  app_id uuid NOT NULL REFERENCES apps(id),
  version_code bigint NOT NULL CHECK (version_code >= 0),
  version_name text,

  created_at timestamptz NOT NULL DEFAULT now(),

);

CREATE TABLE blobs (
  sha256 text PRIMARY KEY CHECK (sha256 ~ '^[0-9a-f]{64}$'),
  byte_size bigint NOT NULL CHECK (byte_size >= 0),
  object_key text NOT NULL UNIQUE,
  state text NOT NULL CHECK (state IN ('staged','verified','quarantined','unavailable')),

);

  source_variant_evidence jsonb NOT NULL DEFAULT '{}',
  validation jsonb NOT NULL DEFAULT '{}',

);

CREATE TABLE set_files (
  set_id uuid NOT NULL REFERENCES artifact_sets(id),
  entry_key text NOT NULL,

  module_name text,
  split_id text,

-- Publication invariants belong in a transaction/service boundary, not JSON alone:
-- * Exactly one base; complete dependencies; package/version/signer coherence.
-- * Every referenced object exists, is verified and is available.
-- * Rule evidence and policy belong to the same app and supported set.
-- * Once published, set membership, profile revisions, rules and plans are immutable.
-- * Withdraw access by state/policy changes; never mutate signed content in place.
-- Use separate database roles to restrict writes to published rows and object keys.
-- Keep an append-only audit of withdrawals, validation and policy changes in production.
-- This draft was reviewed structurally; it has not been run against PostgreSQL.
Publication rules, indexing and safe transactions
  • Use a transaction to publish set membership, capture evidence and verified state together. Upload and verify every required object first.
  • A partial unique index allows at most one base file per set; the publish validator must require exactly one and close all required dependencies. It must also check package, version, signer, roles and targeting.
  • Enforce policy/app/set coherence and rule evidence in the service’s transaction boundary. Do not use a row-level CHECK as a substitute for cross-table validation.
  • Use typed, versioned JSON selectors. Begin with measured profile classes and source evidence; never infer full compatibility from filenames.
  • Index release lookup by app/version, membership by blob hash, and due jobs by state/time. Add extracted selector columns only when real query measurements justify them.
  • Claim due jobs in a short transaction using row locks and SKIP LOCKED; release the transaction before downloading. Use leases and fencing tokens so an expired worker cannot publish over its replacement. [24]
  • Use restricted database roles to freeze published membership, descriptors and profile revisions. Withdraw content through explicit state/policy changes. Keep an append-only production audit.

From an apkeep download to trusted inventory

Collection is not complete when a downloader exits. It is complete when the required files have been checked, stored and published as one coherent result.

  1. Schedule one useful job. Identify app, collector-profile revision and collection generation. Repeated requests join that job. A later refresh receives a new generation.
  2. Download into a new staging directory. Save the actual source result and execution context. Distinguish no access, transient transport failure, authentication failure and incomplete output.
  3. Inspect the originals. Read manifests; verify APK signatures and signing lineage; record versionCode, split IDs, dependency links, native ABIs, density/language targeting where available, and required assets. Scan new content.
  4. Hash and deduplicate. Write missing content-addressed objects, preserving original bytes. Existing hashes reference existing verified objects. A hash proves byte identity, not publisher trust or compatibility.
  5. Publish atomically. Only after object availability and completeness checks succeed, commit the set and capture records. Orphaned staging objects can be cleaned after a grace period.
  6. Validate support. Record installation, update and core-function checks for supported device classes. Enable a compatibility rule only with adequate evidence.

Keep failures specific. A generic “invalid app response” does not prove the app is globally unavailable. Store the observation, retry only when appropriate, and use Attention for authentication or ambiguous cases. A rejected set is quarantined; it does not become a partly functional download.

Collector wrapper pseudocode
job = lease_due_job_with_fencing_token()
result = run_apkeep(job.profile, fresh_directory(job.id, attempt))
observation = inspect_result(result)  // inspect files, not just exit status

if observation.cannot_form_complete_set:
    record_attempt_and_classify_failure(job, observation)
    return

files = verify_original_files_and_dependencies(observation)
for file in files:
    ensure_verified_object_exists(file.sha256, file.bytes)

transaction:
    assert_current_lease_token(job)
    release = upsert_actual_release(files)
    set = insert_or_find_immutable_set(release, canonical_descriptor(files))
    record_capture(job, set, observation)
    mark_job_ready(job)

// Compatibility approval is evidence-based, not implied by this transaction.

Quarantined hashes remain blocked even if a duplicate capture arrives. A previously valid set can later be withdrawn; re-check set/blob states when issuing new plans and access URLs. Queue state must survive process restarts.

How the server chooses the right files

The client describes the phone. The server applies policy and returns one verified shopping list. Country selection does not require a different APK Station client for each market.

  1. Normalize device information. Read SDK, ABI order, density, locales, relevant features and installed package state from the Android client. A website cannot reliably infer all of these from a browser user agent.
  2. Check catalog context. Apply APK Station’s current availability policy using its chosen account/catalog-region model. Keep language separate. Source collector country is provenance, not automatic worldwide distribution authorization.
  3. Find a supported release and complete set. Check the validated compatibility rule, signing identity, required modules/assets and current blob availability. Prefer the appropriate compatible upgrade rather than a globally highest versionCode.
  4. Return a precise result. Ready, acquisition pending, context required, region unavailable, unsupported device, or unsupported runtime dependency. Do not silently substitute an arbitrary APK.

    Selection invariants and the later composition engine
    The minimum viable resolver selects complete sets with established rules.     Yes: generate the XAPK on demand
    

    On-demand generation is our proposed implementation, not an automatic apkeep feature. The XAPK is a delivery package assembled from existing verified files. It does not normally contain the entire server inventory.
    

    First matching request
    Resolve the device and region context. If files are missing, collect them first. If the selected set is ready but no matching XAPK exists, queue one export job, assemble the archive, publish it and return a download URL.
    Later matching requests
    Reuse the cached archive when the selected content and packaging options match. A matching Kenya request can reuse the same bytes as a US request after its own policy check. No separate regional archive is needed when content is identical.
    


    Your native Android client can skip XAPK. It can download the exact files in the signed plan and install them together. Keep XAPK as an export for browsers, offline transfer and customers who need a single file.
    

    What is inside one export?
    Example XAPK for a verified ARM64 / English / 480 dpi set:
  supported XAPK manifest / metadata
  base.apk
  config.arm64_v8a.apk
  config.xxhdpi.apk
  config.en.apk
  required feature / expansion files, if this set needs them

It does not include every other language, processor, Android build or region.
    Use a packager with an explicitly tested XAPK structure and consumer compatibility. An arbitrary ZIP renamed to .xapk is not enough to establish interoperability. A larger archive can be a separate product feature, but only where the chosen installer understands its alternatives; do not assume any XAPK installer can select among arbitrary regional or SDK builds.
    

    Export algorithm, cache identity and archive integrity
    POST /apk/v3/exports { planId, format: "xapk" }

authorize_request_and_recheck_current_policy(planId)
set = require_verified_complete_set(planId)
key = (set.digest, "xapk", packagerRevision, optionsDigest)

if usable_ready_export(key):
    return ready(scoped_short_lived_url)

job = insert_or_reuse_unique_export_job(key)
return 202 pending(job.id)

worker:
    claim job with lease + fencing token
    read immutable originals; verify hashes
    package unchanged APKs with tested metadata and safe paths
    upload to temporary export object
    finalize archive; record SHA-256 and size
    atomically publish ready state after upload completes
    Normalize entry order, timestamps and packaging metadata if reproducible archive bytes are desired. Preserve inner APK bytes, even if ZIP compression choices differ. Include packager version and all content-changing options in the cache key. Keep archive URLs outside signed content identity; deliver them through separate short-lived grants bound to the selected hashes.
    One unique export row prevents a thousand identical requests from starting a thousand builders. Expired leases can be reclaimed; invalid archives never become ready. Archive expiry frees cache storage without deleting canonical APKs. Policy withdrawal stops new grants; existing grants have a bounded lifetime and may require CDN revocation for urgent blocks.
    

    


    10 /
    Install and update as one coherent operation
    

    The native client verifies the plan and downloaded files, stages the complete required APK set in a PackageInstaller session, and handles the actual platform result. Android supports split files belonging to one application; the installer must satisfy package, version and signing constraints. [22]
    


    Updates
    Send installed version, signing identity and modules when resolving. Preserve required installed functionality. An update must have a supported signing relationship and a suitable version; do not silently downgrade or uninstall the existing app. Keep last-compatible releases for the supported fleet.
    Configuration changes
    A changed language, device configuration or requested feature may require another compatible set. Re-resolve, then apply a complete validated change. Avoid promising that the original XAPK automatically contains every future language or module.
    

    Download resumption and local file reuse can reduce transfer. This means reusing verified complete files already in the client cache; it does not imply that partial APK byte patches or arbitrary split reuse across versions are safe.
    

    Client implementation checklist
    • Collect capabilities with Android APIs, including ordered ABIs and locales. Add page-size and hardware details only where the supported resolver needs them.
    • Validate the server’s signed descriptor, expected publisher signing identity, expiry, file size and SHA-256. Reject unexpected archive paths, missing required pieces and incompatible signers.
    • For a normal full-install session, stage all required base/configuration/feature APKs selected by the plan. Handle expansion files through a separately supported path; do not pass an OBB as an APK.
    • Use resumable downloads and atomic local cache promotion. Require enough free space for download, staging and installation.
    • Handle user confirmation and platform errors. Submitted commit is not success. A minimal receipt records installed, cancelled or failed after the OS result.
    • Test fresh install, upgrade, interruption, storage exhaustion, signer mismatch, missing split, stale plan and user cancellation on real Brax devices.
    

    


    11 /
    A small, explicit API
    

    A download URL alone cannot describe compatibility or unfinished collection. Return a decision and a stable job or plan identifier.
    

    EndpointPurposeKey responses
    

    POST /apk/v3/resolveResolve app + capabilities + installed state + catalog context.200 ready/up-to-date; 202 acquisition pending; 422 context required/unsupported; 403 region unavailable; 409 installed-state conflict.
    

    GET /apk/v3/jobs/{id}Read an authorized acquisition/export job.200 with queued/running/ready/retry/attention/failed state; retry guidance. Ready acquisition asks the client to re-resolve.
    

    POST /apk/v3/exportsRequest XAPK for an authorized plan.200 existing ready export; 202 build pending; 409 stale/withdrawn plan.
    

    GET /apk/v3/exports/{id}Read export status and obtain a fresh authorized grant.200 status; ready includes URL, archive hash and size. Recheck policy before issuing access.
    

    POST /apk/v3/install-receiptsOptional minimal client installation outcome.202 accepted. Receipt is telemetry, not proof of global compatibility.
    

    

    Example resolve request and ready descriptor
    Request
    {

    Ready response

  "planId": "<uuid>",

      {"role": "base", "sha256": "<sha256>",

    Examples use placeholders. Configuration files are omitted from this short JSON; a real ready response must list every required file. Sign the canonical descriptor, including all file entries, using APK Station’s manifest key—not a key used to re-sign publisher APKs.
    

    API invariants and privacy
    Clients supply capabilities and a proposed catalog context; authorization derives from the server’s account/catalog policy, not a trusted client-controlled country flag. This architecture does not require GPS or a Google account on every customer’s phone.
    For pending results, return jobId, statusUrl, a reason code and retry guidance. Re-resolve after acquisition because source version and policy may have changed. Acquisition Ready means inventory was published; a deliverable plan additionally requires a validated compatibility rule. If evidence is still being evaluated, expose validation_pending and continue that work instead of downloading the same files again.
    Use idempotency keys for repeated requests and content identity for shared exports. Authenticate access to job/plan records; unguessable IDs are not authorization. Keep collection credentials, source account details and network routing out of customer plans. Log profile IDs and redacted errors, not tokens or complete sensitive source responses. Define retention for capability requests and optional installation receipts.
    

    


    12 /
    What the architecture does—and does not—solve
    

    ConcernImplementation choiceLimit to communicate
    

    Storage duplicationHash original files and reuse one canonical object. Keep replicated durability copies independently.Saves duplicate byte storage; storage still grows with genuinely different content.
    

    Collector bandwidthSchedule useful profiles, avoid duplicate jobs, compare returned hashes.Stock apkeep may transfer identical bytes again before your backend discovers the match. Stored-byte savings do not automatically eliminate upstream traffic.
    

    CoveragePrioritize real Brax devices, launch markets and demanded gaps. Retain source observations.Several phone captures cannot establish complete publisher inventory. A default device profile does not cover all Android devices.
    

    Versions and rolloutPreserve actual versions and last-compatible releases. Refresh captures by context.Historical retrieval through apkeep’s Play adapter is not assured; regional accounts can receive different versions.
    

    On-demand features / gamesValidate PAD, OBB and dynamic-module behavior separately; accept publisher feeds when possible.Initial APK collection does not guarantee later modules or assets. A ZIP container cannot reproduce Play services. [15]
    

    De-Googled runtimeTest login, billing, push and integrity-sensitive behavior on the target OS.Installable, signature-verified and functionally working are separate states. [21]
    

    Access and distributionKeep publisher/source provenance and per-app distribution policy as catalog data.Successful collection does not establish permission or customer entitlement. Archive packaging does not alter those facts.
    

    Platform installation rulesTrack installer restrictions, signing lineage, target API limits and applicable verification requirements.Evaluate the actual Brax OS, certification and distribution route; neither XAPK nor a region label removes platform rules. [25][26]
    

    Bad or withdrawn contentQuarantine by hash/set, revoke rules, stop new grants and invalidate exports as required.Policy state changes independently of immutable bytes. Include access-grant expiry in the withdrawal plan.
    

    

    Publisher cooperation improves completeness
    Accept publisher-provided signed APK sets and targeting metadata when available. Google’s generated-APK API serves authorized publisher access; it is not a public consumer inventory endpoint for any app. If accepting AABs, arrange publisher-controlled generation and signing that preserves the intended update identity. [28]
    

    Retention without breaking updates
    Keep current and last-compatible releases for supported cohorts. Preserve files referenced by retained sets, live plans, supported installations and active jobs. Retire unsupported sets deliberately; delete unreferenced blobs only after a grace period and a fresh reachability check. Apply a separate size/age budget to generated XAPK exports.
    

    Measure the actual benefit
    Report unique stored bytes versus all captured bytes, ready coverage weighted by real requests, install and update success by device class, cache-hit rate, acquisition/export latency, quarantine count and unsupported runtime dependencies. Separate “not yet collected” from “known unsupported.”
    

    Security and operational boundaries
    • Run downloaders and archive parsers with limited filesystem/network access, bounded files, timeouts and size limits. Validate archive paths and reject traversal, duplicate destinations and decompression bombs.
    • Keep private canonical storage behind scoped delivery grants. Only verified published files can be served; object presence is not a permission decision.
    • Verify expected publisher identity and valid signing lineage as well as cryptographic signatures. Sign store descriptors independently and define manifest-key rotation.
    • Protect concurrent jobs with uniqueness, leases and fencing; publish export state only after complete upload. Periodic workers recover expired leases.
    • Collect bounded structured telemetry with correlation IDs, profile revision and outcome codes. Set retry budgets per account/context; surface sustained authentication failures for attention.
    • Back up the database and protect object durability. Exercise restoration so file references and objects remain consistent.

    Fit this into the existing APK Station
    

    Known from this conversation: apkeep is your backend downloader. The public API reviewed earlier exposes download by package/UUID and optional versionCode, with URL/MD5 output and asynchronous retrieval on cache miss. Its download request does not expose SDK, ABI, density or locale. That does not establish what the private backend already supports. [27]
    The private backend/UI repositories returned not-found/not-authorized in this session. Their database, deployed apkeep build, worker routing and Android installer code were not inspected.
    

    PhaseBuildEvidence needed to finish
    

    1 · Establish the real inventoryAudit deployed apkeep version/flags and output. Collect a proposed sample of 100 launch apps on supported profiles. Parse manifests, hashes, signatures and actual file sets.Measured duplication and coverage; no assumption that every app has 88 files.
    

    2 · Store files and capturesAdd canonical blob storage, set membership, collector profiles, capture records and durable jobs. Preserve provenance while importing existing APK/XAPK files.Repeated collectors share bytes; interrupted downloads never publish partial sets; original APK hashes remain unchanged.

    Acceptance scenarios
    1. Matching US and Kenya captures produce two observations, one set and one copy of each APK.
    2. A French-only file is new storage; shared base/processor/density files retain identical hashes.
    3. A partial or mismatched capture cannot produce a ready installation plan.
    4. A country denial is enforced even when an identical XAPK is already cached for another request.
    5. An uncaptured French/320 dpi combination stays pending until a complete compatible set is available.
    6. A worker crash is recovered through lease expiry; stale workers cannot overwrite newer results.
    7. A compatible installed app updates without uninstalling first; cancellation and signer mismatch preserve a clear outcome.
    8. Adding/removing archive cache entries never removes canonical files referenced by supported sets.
    

    


    14 /
    Decisions to carry into implementation
    These are proposed architecture decisions. Their IDs provide stable references for an engineering handoff; they should become accepted ADRs after review against the real codebase.
    

    DecisionChoice and reasonConsequence / alternative
    

    ADR-001 · Original-file storageContent-address original signed APKs. Identical bytes are reusable without changing publisher identity.Reject merged/re-signed “universal” shortcuts. Pay for genuinely different files and durability replicas.
    

    ADR-002 · Complete-set MVPPreserve coherent captured sets; attach compatibility evidence separately.Fewer unsafe assumptions. Cross-capture composition is deferred until provenance, targeting and tests establish it.
    

    ADR-003 · Relational catalogPropose PostgreSQL for identities, references and transactional publication; object storage for bytes.The real stack is unverified. An existing relational database may satisfy the same invariants without a migration to PostgreSQL.
    

    ADR-004 · Server-side selectionThe client submits facts; the backend selects and authorizes a set.One shared rules implementation. A fully offline client would need separately distributed, versioned policy/selection data.
    

    ADR-005 · XAPK as an exportBuild on demand and cache by exact content and packager options.First-request packaging latency. Avoid permanently prebuilding every device/country combination; native delivery bypasses archives.
    

    ADR-006 · Explicit source uncertaintyTreat Play downloads as observations, not the publisher’s complete inventory.Report gaps honestly. Publisher feeds can improve completeness without changing the canonical storage model.
